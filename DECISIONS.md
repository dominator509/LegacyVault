# Decisions

| ID | Decision | Rationale | Status |
|---|---|---|---|
| ADR-001 | Modular monolith before microservices | Lowest cost and operational burden | Accepted |
| ADR-002 | Structured verified facts are authoritative | Prevents model hallucination from becoming record truth | Accepted |
| ADR-003 | DeepSeek only through an isolated gateway | Centralizes privacy, policy, cache, and replacement | Accepted |
| ADR-004 | DeepSeek AI is optional per household | Consent and vendor-risk control | Accepted |
| ADR-005 | Do not collect vault secrets at launch | Reduces catastrophic exposure | Accepted |
| ADR-006 | Manual production deployment | User did not authorize automatic deploy | Accepted |
| ADR-007 | Concierge-assisted launch | Produces revenue and workflow evidence earlier | Accepted |
| ADR-008 | US-only launch until counsel expands scope | Limits legal surface | Accepted |
| ADR-009 | Continue independent engineering while EP-000 remains externally unverified | Explicit operator instruction requires maximum local completion; the original node, preflight sentinel, graph dependency, legal gates, and production ship gate remain unchanged and no external result may be fabricated | Accepted for this run |
| ADR-010 | Add explicit bootstrap diagnostics, package metadata inspection, local environment, Compose, and migration commands | `ENVIRONMENT.md`, the operator's unattended-run requirements, and the EP-001 toolchain scope require reproducible commands that were absent from `COMMANDS.md` | Accepted |
| ADR-011 | Generate the pnpm lockfile only on the first EP-001 install and freeze every later install | The original install gate failed with `ERR_PNPM_NO_LOCKFILE` while EP-001 is explicitly responsible for creating `pnpm-lock.yaml` | Accepted |
| ADR-012 | Use pinned PostgreSQL 17, Valkey, MinIO, and Mailpit containers for real local protocols | The blueprint explicitly permits protocol-compatible local infrastructure; these services cover database, queue/cache, S3, and SMTP without claiming hosted-provider verification | Accepted for local and test only |
| ADR-013 | Add `LOCAL_*` variables only for ignored development configuration | Compose requires credentials that must not reuse production provider secrets; the generator creates independent values and production configuration rejects local engineering mode | Accepted for local and test only |
| ADR-014 | Make database and Redis probes protocol-real and shell-portable | The database probe passed in login Git Bash but failed from preflight because `psql` was not on the non-login path; the Redis probe incorrectly targeted an undeclared HTTP URL and could not validate `REDIS_URL` | Accepted |
| ADR-015 | Use GNU `timeout` only when positively identified and bound each local probe internally | Git Bash resolved `timeout` to Windows `timeout.exe`, which returned exit 1 for POSIX syntax and made every credential look invalid | Accepted |
| ADR-016 | Format implementation artifacts but exclude immutable blueprint prose and generated lockfiles | The first format check reported 60 files, predominantly L1-L4 control documents that must not be mechanically rewritten | Accepted |
| ADR-017 | Permit one explicit lock refresh after reviewed exact manifest changes, followed by frozen install and audit | Workspace packages and approved dependencies added by later graph nodes must update the lockfile without making ordinary installs mutable | Accepted |
| ADR-018 | Pin the official ClamAV 1.4.5 Debian slim image by digest and expose clamd on loopback only for local document scans | The blueprint requires local malware scanning; the exact image digest makes local proof reproducible and does not imply hosted production verification | Accepted for local and test only |
| ADR-019 | Run the pinned OCRmyPDF 17.8.1 image as an ephemeral network-disabled, read-only, resource-bounded local process | This proves the blueprint's local OCR path on Windows without installing a mutable host Python toolchain or granting a persistent service access to document data | Accepted for local and test only |
| ADR-020 | Persist only normalized Stripe subscription fields and order updates by provider creation time | Raw billing payloads are unnecessary sensitive data; unique external identifiers, signed tenant metadata, and monotonic provider timestamps provide replay and event-order protection | Accepted |
| ADR-021 | Store the local export signing key as base64-encoded Ed25519 PKCS8 DER and the local application KEK as exactly 32 random bytes; narrowly repair those values in existing ignored environments | The initial generator encoded PEM text and generated a 48-byte AES key while the application requires unambiguous Ed25519 material and AES-256; rotating database and service credentials would break persistent local infrastructure unnecessarily | Accepted for local and test only |
| ADR-022 | Pin Better Auth 1.6.26, its matching passkey plugin, and `@node-rs/argon2` 2.0.2 | The blueprint mandates Better Auth, WebAuthn passkeys, TOTP, and Argon2id fallback; exact matching versions were verified from the package registry before composition | Accepted |
| ADR-023 | Compile Better Auth schema SQL through the installed 1.6.26 `getMigrations` API and review it before adding a numbered application migration | The separately published CLI is pinned to an older 1.4.21 core and would invent a version mismatch; the installed library exposes a matching read-only compiler | Accepted |
| ADR-024 | Link Better Auth users to tenant memberships through nullable `memberships.auth_user_id` with one membership per user per household | Authentication identities are global while authorization is tenant-scoped; the bridge permits explicit household selection without placing tenant columns on Better Auth's provider-owned tables | Accepted |
| ADR-025 | Treat compliance documents as fail-closed engineering traceability and templates, never as evidence of external approval | The blueprint requires technical policy-to-code artifacts while counsel, vendor, insurance, executive, and regulatory determinations remain operator-owned external evidence | Accepted |
| ADR-026 | Persist owner-approved support access as a separate tenant-RLS record bounded to four hours and explicit categories | Support access is a temporary approval event, not a standing membership permission; a separate revocable record preserves least privilege and auditability | Accepted |
| ADR-027 | Derive the authorization category from the canonical prefix of persisted fact field keys and use fixed action-purpose identifiers at API boundaries | Persisted field keys already group facts under the canonical record categories; deriving from stored state prevents a client from claiming a less sensitive category, while fixed purposes prevent ambient grant reuse | Accepted |
| ADR-028 | Treat consent withdrawal as a versioned idempotent write and retain the original grant record | Consent evidence must preserve what was accepted and when it was withdrawn; an optimistic transition prevents silent overwrite while idempotency makes retries safe | Accepted |
| ADR-029 | Make the production authorizer append content-free allow/deny decisions to the immutable tenant audit chain and fail closed when audit append fails | Authorization without durable decision evidence violates the security boundary; using the same tenant context, pseudonymized actor, fixed purpose, category, action, and denial reason avoids payload logging | Accepted |
| ADR-030 | Define portable export v1 as a deterministic encrypted JSON container with an Ed25519-signed public envelope manifest and per-entry SHA-256 integrity records | The blueprint requires encrypted portability and signed manifests but does not prescribe an archive library; the versioned self-describing format uses existing verified crypto, rejects unsafe paths, hides tenant content, and requires an independently trusted public key | Accepted |
| ADR-031 | Persist each portable export and its wrapped client export key as the subject of an idempotent resumable workflow | Raw export keys must never enter Redis jobs or logs; wrapping under the application KEK and queuing only tenant and workflow identifiers preserves recovery without exposing key material | Accepted |
| ADR-032 | Lazily create one active random DEK per household under a transaction advisory lock and persist only its AES-GCM wrapping under the application KEK | Per-household envelope encryption requires stable recoverable keys without duplicate creation races; tenant RLS, versioned wrapped keys, and zero plaintext persistence establish the boundary needed by records, documents, rotation, and portable exports | Accepted |
| ADR-033 | Make portable exports self-contained by rewrapping the household DEK under the client export key and including encrypted records and document objects | The application must not decrypt every field merely to export it; a client holding the export key can open the signed archive, recover the household DEK, and interpret versioned ciphertext while the worker never persists raw keys | Accepted |
| ADR-034 | Create subscription Checkout sessions without trusting a client-supplied Stripe customer and bind them to the authenticated membership plus signed tenant metadata | Stripe creates a Customer when a subscription-mode session omits `customer`; fixed server URLs, idempotency, an internal client reference, and duplicated session/subscription metadata avoid account confusion and open redirects | Accepted |
| ADR-035 | Use a two-phase direct document upload: issue a one-time client encryption key wrapped under the household DEK, then presign only the resulting ciphertext checksum and persist quarantine state before processing | Satisfies direct signed upload and envelope-encryption requirements without placing plaintext objects in storage; the additive nullable migration preserves expand-migrate-contract for any pre-existing rows while all new writes enforce complete metadata | Accepted |
| ADR-036 | Persist OCR output as a uniquely keyed envelope-encrypted searchable-PDF derivative with its own checksum and provenance row | Searchable content must remain separate from immutable originals, preserve the document encryption boundary, and be independently verifiable without treating OCR output as authoritative fact data | Accepted |
| ADR-037 | Complete provider-independent document classification through an explicit reviewed manual extraction transaction that creates evidence-linked encrypted candidate facts | DeepSeek is optional and unavailable locally; the manual path preserves useful workflows, provenance, idempotency, and the invariant that extracted values remain non-authoritative until separately confirmed | Accepted |
| ADR-038 | Run one queue consumer with only fully composed document-processing and portable-export handlers and fail every unsupported job name explicitly | A missing handler must never produce success; partial fail-closed dispatch lets implemented workflows operate while unfinished deletion, annual-review, and notification jobs remain visibly failed rather than fabricated | Accepted |
| ADR-039 | Limit authenticated DeepSeek live-fire to a fixed synthetic JSON-only prompt on the approved HTTPS host and assert structure plus usage without logging response content | This proves the real credential, model route, structured response, and metering boundary while ensuring no household content crosses the external provider boundary during infrastructure validation | Accepted |
| ADR-040 | Expose AI interview suggestions only through active version-matched consent, explicit category disclosure, read authorization, DLP, schema validation, category confinement, output DLP, and tenant-scoped exact/idempotency caches | Model suggestions remain non-authoritative and unpersisted; this enables the optional provider without weakening manual workflows or allowing prohibited content, cross-category output, duplicate inference, or cross-tenant cache reuse | Accepted |
| ADR-041 | Namespace BullMQ queues by environment and give integration/live-fire runtimes process-unique queue names | A shared default queue let the real development worker consume stale test jobs whose tenant rows exist only in the test database; explicit namespaces prevent cross-environment effects without deleting forensic queue evidence | Accepted |
| ADR-042 | Normalize raster documents with fixed Pillow and pikepdf code inside the same bounded OCR runtime before OCR | OCRmyPDF rejects alpha-channel images and raw images may retain metadata or contain decompression bombs; explicit Python runtime configuration plus a fixed 100-page and 50-megapixel limit produces a metadata-free RGB PDF while PDF inputs receive structural page-count validation | Accepted |
| ADR-043 | Make privacy deletion a self-confirmed, optimistic, recoverable state machine that removes attributable account access after the configured delay and stops at explicit shared-data and processor review | Household records are not currently attributable to one person and proposed retention periods lack counsel approval; destructive inference would risk deleting collaborators' data, while recording legal holds, retained categories, backup expiry, and contract-verification-required processor rows preserves honest, resumable evidence | Accepted; supersedes ADR-038 handler list only |
| ADR-044 | Generate reports and annual reviews only in the worker, persist their payload as a household-DEK envelope, and accept document expiration only as a timezone-qualified timestamp covered by upload idempotency | Reports may contain the most sensitive confirmed, candidate, and disputed vault data, so the API queues only identifiers and the worker decrypts transiently, produces deterministic provenance and review findings, encrypts before persistence, and zeroes plaintext buffers. The additive report columns and legacy plaintext columns are an expand-migrate state for existing installations, not authorization for new plaintext report writes | Accepted; legacy report-column backfill and contract removal remain required before production migration completion |
| ADR-045 | Return reports only from an authorized tenant-scoped `GET /v1/reports/:id` boundary that decrypts completed payloads in memory and returns metadata alone for unfinished workflows | Clients need a canonical way to observe queued work and read completed results without exposing ciphertext, plaintext persistence, cacheable responses, or cross-tenant identifiers; binding the opened payload to its row and tenant detects substitution before rendering | Accepted |
| ADR-046 | Store cache-eligible exact AI results in Redis only as household-DEK envelopes with a 15-minute TTL and a key covering tenant, consent version, complete prompt envelope, model, mode, and output budget; require TLS Redis in production | Shared application caching is needed across API replicas, but model output may contain personal data. Encryption, bounded retention, deterministic isolation and invalidation dimensions, corrupt-entry eviction, post-cache policy validation, content-free hit/miss telemetry, and fail-closed hashed-scope purge before privacy deletion preserve minimization, consent, and deletion boundaries | Accepted; measured production cache targets remain required |
